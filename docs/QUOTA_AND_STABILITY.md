# 排序稳定性与额度保护

`v4.7.1-lee.3` 修复账号排序 panic，并改进模型档位兼容和额度保护。4.7.12 合并后的取舍见 [同步说明](UPSTREAM_4_7_12.md)。

## 错误原因

原排序将两个重置时间相差不足十分钟视为相等，这种相等关系不满足传递性，可能触发 Rust 的排序 panic。HTTP 连接因此断开，下游 New API 将 EOF 包装为 HTTP 500 和 `do request failed`。现在使用固定十分钟时间分组、可全序比较的健康度和稳定账号 ID，避免排序崩溃。

New API 可能将 `gemini-3.8-flash-high` 拆为 `gemini-3.8-flash` 与 `reasoning_effort=high`。实测基础型号返回 429，而完整型号正常。4.7.1 Lee 的 OpenAI 入口曾根据独立 effort 恢复账号实际提供的 Flash 型号。4.7.12 起采用官方模型档位路由及统一思考流水线，不再保留该旧 helper；显式型号仍交由官方规则处理。

## 额度保护

- 周额度与五小时额度共同限制可用余额，取更低者；旧实现优先使用五小时额度，可能漏掉已接近耗尽的周额度。
- 选号优先检查实际模型的额度，缺少实际型号记录时采用额度组的保守值。
- 达到阈值即保护，即 `remaining <= threshold`；旧逻辑只处理严格小于阈值。
- 检查位于候选快照过滤阶段，固定账号、会话绑定和失败换号均从过滤后的候选中选择。
- 请求结束或客户端断开后，后台刷新已用账号的额度并更新内存。相同账号合并刷新，最多每五秒启动一次，单次刷新请求有十秒超时；刷新期间，受保护模型不继续选择该账号。
- 从最高订阅等级的全部可用账号中采样，不再固定只用前五个。仍优先选择采样中目标模型额度较高的账号。
- 刷新账号或短暂等待失败不会再直接清空限流记录，其他模型还有额度不能成为解除限流的依据。

配置中的保护开关、监控模型和阈值继续生效。部署本次用户请求时将阈值设为 10%。未知额度和供应商延迟更新无法作为精确的可用预算；已发出的请求可能继续消耗额度。因此不能承诺物理上精确保留 10%，但已确认达到阈值的账号不会再通过选号检查。

首次加五次换号的上限保持不变。上层 New API 仍可能再次重试整个请求，因此端到端的请求次数不等于单次 Antigravity 请求的六账号上限；本次没有更改 New API 全局重试设置。
