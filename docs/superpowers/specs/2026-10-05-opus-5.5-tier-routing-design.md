# Opus 5.5 动态档位路由设计

## 背景与验证结论

生产服务器的上游目录已经向唯一 ULTRA 账号公布以下物理模型 ID：

- `claude-opus-5-5-low`
- `claude-opus-5-5-medium`
- `claude-opus-5-5-high`

2026-10-05 使用该 ULTRA 账号直接调用 `claude-opus-5-5-high`，上游返回 HTTP 200。上游没有公布无档位的 `claude-opus-5-5`；该 ID 应当作为平台便利别名，不应当原样发往上游。

## 目标

- 保留上游 `low / medium / high` 物理 ID，并继续由动态模型目录控制对外展示。
- 提供稳定的 `claude-opus-5-5` 便利别名，默认路由到 `high`。
- 客户端显式传入 `effort=low|medium|high` 时，将便利别名路由到对应的上游物理 ID。
- 保持 ULTRA 或有明确付费证据的 Pro 账号限制、adaptive thinking、token 统计和成本计算语义不变。

## 方案对比

| 方案 | 优点 | 代价 | 结论 |
| --- | --- | --- | --- |
| 动态物理 ID + 条件式便利别名 | 兼顾真实目录、客户端易用性和未来失效自愈 | 需要增加一层共享路由规则 | **采用** |
| 仅暴露三个物理 ID | 不需要修改路由 | 客户端必须理解上游档位命名 | 不采用 |
| 静态写死别名和物理 ID | 实现直接 | 模型失效时仍需重新发版 | 不采用 |

## 路由设计

### 物理 ID

客户端直接请求 `claude-opus-5-5-low`、`claude-opus-5-5-medium` 或 `claude-opus-5-5-high` 时，路由层保留原 ID，不自动升级或降级。上游不提供所请求档位时，返回真实上游错误。

### 便利别名

`claude-opus-5-5` 按客户端思考档位路由：

| 客户端档位 | 上游物理 ID |
| --- | --- |
| 未指定、`high` 或不可识别值 | `claude-opus-5-5-high` |
| `medium` | `claude-opus-5-5-medium` |
| `low` | `claude-opus-5-5-low` |

路由函数必须放在共享模型层，Claude、OpenAI Chat Completions、OpenAI Responses 和 Gemini 协议共用同一语义。用户自定义映射的目标是 `claude-opus-5-5` 时，也应当应用相同档位规则。
Claude 入口选档使用客户端原始 effort 提示；思考预算兼容处理改写后的 `output_config.effort` 只保留其原有预算用途。配置映射只应用一次，映射目标为便利别名时再选档，不继续查找第二条自定义映射。

## 动态目录

- 物理 ID 仍完全来自 fresh / last-known-good 上游快照。
- 仅当动态快照中出现 `claude-opus-5-5-low`、`claude-opus-5-5-medium` 或 `claude-opus-5-5-high` 这三个精确物理 ID 之一时，才向普通模型目录追加 `claude-opus-5-5` 便利别名；带供应商前缀、点号版本或其他后缀均不触发。
- 启用 `only_raw_quota_models` 时，只返回上游物理 ID，不追加便利别名。
- 快照中最后一个 Opus 5.5 物理 ID 失效后，便利别名随快照过期规则自动消失，不需要 CI/CD 发版。

## 账号与计费语义

- 现有 `is_adaptive_thinking_model` 已按 `claude-opus-5-5` 前缀识别三个档位，不增加特殊分支。
- 现有账号筛选已允许 ULTRA 和有明确付费证据的 Pro，禁止 Free 和无付费证据的 Pro。
- 现有价格匹配使用同一前缀规则，三个档位继续按 Opus 5.5 的 input、output 和 cache read 价格统计。
- adaptive thinking 只保留 `includeThoughts=true`，不向上游发送手工 budget。

## 错误处理

- 物理 ID 明确不存在时，继续使用现有的终止跨账号重试语义。
- 便利别名不使用静默的跨档位降级。客户端选择 `high`、`medium` 或 `low` 后，该档位就是请求语义。
- 模型目录刷新失败时，保留现有 last-known-good 行为。
- 不改写账号凭据、代理绑定、保护模型或账号排序。

## 测试与验收

### 单元测试

- 无 effort 的 `claude-opus-5-5` 路由到 `high`。
- `low / medium / high` effort 分别路由到对应物理 ID。
- 三个物理 ID 在所有协议中保持不变。
- 自定义映射到便利别名时仍应用 effort 路由。
- 动态快照包含任一 Opus 5.5 物理 ID 时，普通目录包含便利别名。
- raw-only 目录不包含便利别名。
- 快照不再包含 Opus 5.5 时，便利别名消失。
- 三个档位仍命中 ULTRA / 付费 Pro 筛选、adaptive thinking 和 Opus 5.5 价格。

### 预检

- `cd src-tauri && cargo fmt -- --check`
- `cd src-tauri && cargo clippy --all-targets --all-features`
- 执行模型路由、目录、Opus pipeline 和 token 统计的定向测试。
- 若修改前端代码或前端配置，再执行 `npm run build`；本设计不要求前端静态写死模型。

### 生产验收

1. 只部署已推送且 CI 通过的精确 commit / image digest。
2. 验证 `/api/proxy/models`、`/v1/models`、Claude Models API 和 Gemini Models API 都使用同一目录语义。
3. 使用 ULTRA 账号通过普通客户端协议调用 `claude-opus-5-5`，确认对外别名已路由到上游物理档位。
4. 验证账号数量、代理绑定、token 统计数据和服务健康状态未回归。

## 非目标

- 不新增静态前端模型表。
- 不为 Sonnet 5.5 新增便利别名或特殊路由。
- 不修改账号调度、重试次数、额度保护和代理选择策略。
- 不解决后台额度刷新用旧快照覆盖新 access token 的独立并发问题。
